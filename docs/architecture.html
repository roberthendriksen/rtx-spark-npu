Sparky's NPU: hardware and software architecture

The NPU is an NVIDIA Deep Learning Accelerator, the fixed-function accelerator of the Jetson boards. One software stack reaches it: TensorRT's DLA backend compiles a model, and cuDLA runs it through a CUDA stream.

Where it sits

The NPU is a block on the same chip as the CPU and GPU. It has no memory of its own, and Windows lists it as a second adapter of the GPU's driver.

Shared memory. Weights, tensors and the compiled model live in the same LPDDR5X as everything else. The NPU reaches them by DMA through the IOMMU.

Clock. The limit is 1562 MHz. Under full load it reached 1105 MHz, on AC and on battery, with the Windows Standard power plan.

One driver. There is no separate NPU driver to install. nvlddmkm.sys serves the GPU as a display adapter and the NPU as a compute-only one.

Inside the accelerator

A convolution pipeline with a few side units. The convolution core does almost all the work, at about 1,940 multiply-accumulates per clock cycle.

Why wide layers are slow. A 3×3 layer with 512 channels has 4.7 MB of weights, more than the reported 2.5 MiB buffer. Throughput falls from 4.3 to 1–2.7 TOPS.

Why depthwise is slow. A depthwise convolution keeps only about 30 of the roughly 2,000 multipliers busy per cycle.

FP16 only. The compiler knows INT8 and sparse weight formats, but on Windows on Arm only FP16 compute is offered. Sparse weights ran no faster.

The software stack

Compiling and running are separate. TensorRT is only needed to compile. At run time one small DLL from the CUDA toolkit talks to two DLLs that ship with the driver.

How it was found. REA's export and import inspectors showed that nvcudla.dll has one cudlaDrv* function for each function of NVIDIA's public cuDLA API. Nothing was decompiled.

Kernel entry. nvdla_runtime.dll calls the Windows graphics kernel (D3DKMT*): open the adapter, create a context, submit, wait on a sync object.

Dead ends. cuDLA's standalone mode returns "unsupported". TensorRT could not build a GPU engine on this platform. DirectML and Windows ML are reported not to work.

One inference, in hybrid mode

Every NPU task passes through the GPU's CUDA stream on the way in and on the way out. That is the only mode that works, and it explains the two timing surprises below.

A busy GPU slows the NPU. With another process saturating the GPU, the two hops through the stream wait their turn: NPU latency roughly doubles. The GPU job lost about 5%.

It wakes slowly. After half a second with nothing on the GPU, the next task can take 0.2–0.9 s. A tiny task every 100 ms prevents it.

Floor. A near-empty task takes 0.36 ms, so models that already run in under a millisecond on the CPU gain nothing.

How fast it is

About 4.3 TOPS on ordinary convolutions, much less on very wide layers, transformer encoders and depthwise convolutions. The advertised figure is ten times higher and not reachable.

Against the CPU

Mid-size and large networks run two to four times faster than on eight CPU threads. A small one keeps its lead only while the GPU is idle.

Waking up

Left alone for half a second or more, the next call can take hundreds of milliseconds. A tick during the gap keeps it near ten.

What a model has to look like

Static shapes, batch 1, FP16, 4-D tensors, and every layer on the NPU. A transformer as PyTorch exports it is rejected; the same network rewritten with 1×1 convolutions compiles.

What to use it for

Good fits

  • Text or audio embedding encoders with a fixed length: 4–25 ms.
  • Speaker, keyword or audio classifiers built from ordinary convolutions.
  • ResNet-style image classifiers and detectors at a fixed resolution (not run here).
  • Any of these while the GPU is busy with a language model, at about half speed.

Poor fits

  • MobileNet-style networks: depthwise convolutions are about 60 times less efficient.
  • LSTM or GRU models, autoregressive decoders, language models, dynamic shapes.
  • Models that take under a millisecond on the CPU.
  • Occasional calls without a keep-warm tick.

Software under test: driver 621.24 (32.0.16.2124), CUDA UMD 13.5, cuDLA 13.5.25, TensorRT 11.5.0.63. DLA support in TensorRT on Windows on Arm is a beta.
